06

RLS（アクセス制御）

🔒
RLS（Row Level Security）とは？「誰がどの行を見られるか」をデータベース側で自動チェックする仕組みです。アプリ側の実装に漏れがあってもDBレベルで守れます。
SupabaseのロールとはNext.jsとの関係
anon（未ログイン）
auth.uid()NULL
auth.role()'anon'
ゲスト購入するお客様がこれ。
authenticated（ログイン済み）
auth.uid()ユーザーID
auth.role()'authenticated'
管理者がログインするとこれ。
ポリシー一覧
テーブル操作誰が条件
productsSELECT🌐 全員（ゲスト含む）無条件
productsINSERT UPDATE DELETE🔑 管理者のみrole = 'admin'
ordersINSERT👤 ゲストのみ未ログイン ＋ guest_email あり
ordersSELECT UPDATE🔑 管理者のみrole = 'admin'
order_itemsINSERT👤 ゲストのみ対応する orders がゲスト注文
order_itemsSELECT🔑 管理者のみrole = 'admin'
profilesSELECT🙋 本人 or 管理者id 一致、または admin
cart_items全操作🙋 本人のみuser_id 一致（将来の会員用）
🚨 RLS デバッグ TIPS

permission denied エラーが出たら RLS ポリシーが原因の可能性があります。

📍 確認場所
Supabase Dashboard
→ Table Editor
→ 該当テーブル
→「RLS policies」タブ
🛠 一時的に RLS を回避する方法
-- SQL Editor で実行（確認後は必ず RESET ROLE すること）
SET ROLE postgres;   -- RLS を回避

SELECT * FROM orders;  -- 確認したいクエリ

RESET ROLE;           -- ← 忘れずに！
07

注文処理の流れ（place_guest_order）

フロントから place_guest_order() を1回呼ぶだけで、在庫チェック〜注文作成〜在庫減算をまとめて処理します。

処理のステップ
0
ガードチェック
ログイン済みユーザーなら即エラー（ゲスト専用）
1
カート空チェック
空なら即エラーを返す
2
在庫チェック
1個でも不足 → 全処理中止
3
小計計算
単価 × 数量 の合計
4
orders に INSERT
→ トリガーが注文番号を自動採番
5
order_items に INSERT
商品名・価格をスナップショット保存
6
stock を減算
在庫を注文数分だけ減らす
↩
注文IDを返す
フロントは ID で注文番号を取得 → 完了画面に表示
トランザクションとは？

ステップ4〜6は「一体不可分のひとかたまり」として実行されます。途中でエラーが起きると全処理が自動でなかったことになります（ロールバック）。

❌ トランザクションなしだと…
ステップ4: 注文作成 ✅
ステップ5: 明細作成 ← エラー！
ステップ6: 在庫減算 → 実行されない
→「注文はできたのに在庫が減らない」😱
✅ トランザクションがあると…
ステップ5でエラー → ステップ4も取り消し
→ データが中途半端な状態にならない
フロントからの呼び出し方
const { data } = await supabase
  .rpc('place_guest_order', {
    p_guest_email:  'user@example.com',
    p_shipping_name:'山田 太郎',
    // 住所・電話番号...
    p_cart_items: [
      { product_id: 'uuid...', quantity: 2 }
    ]
  });

// data には注文ID（UUID）が返ってくる
const orderId = data;

全体の流れ
管理者の操作

ボタンをクリック
→
モーダルが開く
配送業者: [ヤマト運輸 ▼]
追跡番号: [__________]
→
① Supabase UPDATE status = 'shipped'
carrier = 'ヤマト運輸'
tracking_number = '...'
② Resend でメール送信 guest_email 宛に自動送信
追跡番号・追跡URLを記載
ℹ️
フロントのモーダルは直接 Supabase を呼ぶのではなく POST /api/ship（Next.js API Route）を経由します。これにより DB 更新とメール送信を1リクエストで安全に処理できます。
コード例（API Route 内）
// app/api/ship/route.ts
import { Resend } from 'resend'; // resend@6.9.4

// ① DB を更新（3カラムを同時に）
await supabase.from('orders').update({
  status:          'shipped',
  carrier:         carrier,
  tracking_number: trackingNumber,
}).eq('id', orderId);

// ② メールを送信
const resend = new Resend(process.env.RESEND_API_KEY);
await resend.emails.send({
  from:    'shop@yourdomain.com',
  to:      guestEmail,
  subject: '【なにわセレクトショップ】発送のご案内',
  html:    /* テンプレートHTML */,
});
⚠️
Resend の API キーは .env.local に RESEND_API_KEY=re_xxxxx の形式で保存してください。ソースコードに直接書いたり Git にコミットしたりしないでください。

よくあるエラーと対処法

エラー原因対処
permission denied for table xxx RLS ポリシーが原因 Section 06 のデバッグTIPSを参照
violates check constraint
"orders_user_or_guest"		 user_id も guest_email も NULL guest_email を必ず渡す
duplicate key violates unique constraint
"orders_order_number_key"		 同じ秒に複数注文（ほぼ起きない） 再度注文を試みてください
カートが空です 空の配列を渡した フロントのカート状態を確認
XXX の在庫が不足しています 在庫数を超える注文 フロントの在庫チェックUIを見直す
relation "profiles" does not exist SQL_1 を実行していない SQL_1 → SQL_2 → SQL_3 の順で実行
permission denied（発送モーダル） is_admin() が false を返している profilesのroleが 'admin' か確認
メール送信に失敗しました Resend APIキーが未設定 .env.local の RESEND_API_KEY を確認
メールが届かない 迷惑メール判定など Resend Dashboard の送信ログを確認
