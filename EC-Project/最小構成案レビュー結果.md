# 最小構成案.md レビュー結果

## 1. 良い点

- ECサイトとして最低限動作する「商品一覧 → カート → 決済」の流れが〇で確保されている
- 5人チームの初期目標として、スコープが絞られていて現実的

---

## 2. 重大な問題（このままでは最小構成として機能しない）

### (A) ログイン機能が〇なのに、顧客管理（会員登録）が×

最小構成案.md 20行目でログイン機能は〇だが、19行目の顧客管理（会員登録）が×。**登録できないのにログインはできない**という矛盾がある。

**対応案:** 顧客管理を〇にするか、最小構成ではログイン不要（ゲスト購入）にする。要件定義書(F-01, F-02)では会員登録・ログインが前提なので、**顧客管理を〇に昇格させるのが妥当**。

### (B) 注文確定（在庫減算）が×

最小構成案.md 17行目の「DB上の在庫数を注文数分マイナスする」が×。これがないと、**決済しても在庫が減らず、売り切れた商品を何度でも購入できてしまう**。RFD.mdでも「売り切れなのに注文が入っちゃうのが一番怖い」と明記されており、顧客の最大の懸念に応えられない。

**対応案:** 注文確定（在庫減算）を〇に昇格させるべき。

### (C) カート内商品の削除が×

最小構成案.md 11行目が×だが、削除手段がないと**間違えてカートに入れた商品を取り消せない**。UX上、最小構成でも必須と考える。

**対応案:** カート内商品の削除を〇に昇格。

---

## 3. 要検討（強く推奨）

| 項目 | 理由 |
|---|---|
| **決済完了画面（×）** | 支払確定ボタンを押した後、何も表示されないと注文が通ったか分からない。最低限「注文完了しました」の画面は必要。要件定義書F-11でも注文番号表示が定義されている |
| **在庫0でカートに入れられない（×）** | 在庫減算を実装するなら、在庫0チェックもセットで入れないと整合性が取れない。RFDの「売り切れなら買えないようにして」に直結 |
| **カード決済の入力項目** | 最小構成案では「16桁の数字入力」のみだが、要件定義書F-10では**有効期限・セキュリティコード（3桁）**も定義されている。モックにも3項目ある。最小構成でもモックに合わせるべきか要確認 |

---

## 4. 構成上の軽微な指摘

- **管理者機能がすべて×**: 最小構成では商品データをDBに直接投入する想定と思われるが、その前提を明記しておくとチーム内で認識がずれにくい
- **ログイン機能の詳細欄が「注文内容確認」**: ログイン機能自体の説明ではなく、ログイン後にできることが書かれている。「メールアドレス・パスワードでログインできる」のような記述に修正した方が分かりやすい
- **「おすすめ」が独立した行**: 商品一覧の子項目として整理した方が構成上わかりやすい

---

## 5. まとめ：最小構成で〇にすべき項目の提案

現在の〇に加えて、以下を〇に昇格させることを推奨する:

| 追加すべき項目 | 理由 |
|---|---|
| **顧客管理（会員登録）** | ログインの前提条件 |
| **注文確定（在庫減算）** | 決済の意味がなくなる・顧客最大の懸念 |
| **カート内商品の削除** | 最低限の操作性 |
| **決済完了画面** | 注文成功の確認手段 |
| **在庫0のカート追加不可** | 在庫管理の整合性 |

これらを追加しても、5人チームで段階的に開発する最初の目標として現実的な範囲に収まると考える。
